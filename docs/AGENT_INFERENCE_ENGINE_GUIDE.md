# 推理引擎编写指导规范

适用对象：任何跑在 Agent 上的模型推理工作流——ASR、OCR、版式分析、embedding 等。本规范不绑定某次改动、某个文件名；正文讲架构、设计与算法层面的**前因 → 写法 → 目的**，具备可迁移性。每节末尾用一句话点出"本次 ASR 优化中的实例"，仅作例证，不作规范本身。

阅读方式：MUST 是红线（违反则打回），SHOULD 是强建议（偏离需在 PR 中说明理由与实测数据）。

---

## 0. 三条硬约束（一切规则的来源）

在动手前先接受三个事实，后面所有规则都是它们的推论：

1. **加速器是串行执行的**：同一模型副本在同一块卡上，同一时刻只能做一件事。并行度只能来自"多个模型"或"多块卡"，不能来自"对同一副本加线程"。——推论：第 2、6 节。
2. **推理成本由"资源量"决定，不由"任务个数"决定**： costs ∝ 音频秒数 / 图片像素数 / token 数，而不是 job 个数。按个数拼 batch 必然在长短不一的输入下失衡。——推论：第 3 节。
3. **失败与抖动是常态**：显存不足、驱动丢失、对端超时、畸形输入每天都会发生；上报、心跳、扫盘这类 side-channel 会在你没注意时挤进关键路径。——推论：第 4、5、8 节。

---

## 1. 五段管线与职责边界

**前因**：推理工作天然跨越 I/O、CPU、加速器三种资源。职责混杂（例如解码函数里直接发 HTTP）会把慢速 I/O 钉死在昂贵的加速器时间片里，且无法独立测试。

**写法**：任何引擎都拆成五段，每段单一所有者、单向依赖：

```
摄取(下载/寻址) → 预处理(CPU) → 组批(调度) → 推理(加速器) → 后处理与结算(组装结果、上报)
```

- 推理段 MUST 是**纯计算函数**：输入张量/分片，输出结构化结果；禁止网络调用、禁止落盘、禁止直接上报进度。进度只经回调函数向外抛，由管线层决定节流与合并。
- 重量初始化（权重加载）MUST 移出事件循环（线程池或独立进程），禁止阻塞调度器。
- 每段的失败语义独立：下载失败 ≠ 推理失败，结算失败不污染模型状态；异常向上传播为统一的 job 状态，而不是崩掉 Agent 进程。

**目的**：加速器时间只花在前向计算上；每段可独立做单元测试与性能剖析。

*本次实例：曾把每 batch 的进度 POST 写进推理循环，N 个 batch 就产生 N 次同步 HTTP；改为管线层节流后 POST 量降 5~10x。*

---

## 2. 并发模型：三层、细粒度串行

**前因**：Agent 里有三层执行体——异步事件循环（调度/网络）、CPU 线程池（阻塞任务）、加速器（前向）。最常见的性能事故是"在错误的层加锁"：一个全局锁把本可并行的模型/设备全部串行化，加速器利用率腰斩；反过来，对同一模型副本放行并发则会触发底层算子竞态或显存踩踏。

**写法**：

- MUST 按 **(模型, 设备)** 二元组做串行单元：同一二元组同时只进一个推理，不同二元组允许并行。禁止全局推理锁，禁止新增跨模型/跨设备的互斥。
- 推理期间 MUST 持有模型的生命周期 guard（引用计数/lease），使"卸载"必须等待"在飞推理"排空或超时强卸。卸载与加载串行化，但与无关模型的推理不互斥。
- 并发上限（信号量/队列深度）表达的是**背压**，不是性能目标：上限 = min(下游最窄资源, 显存可容纳副本数)。动态调参只收敛、不泄漏（后台唤醒任务合并为至多一个在飞）。

**目的**：单卡延迟不变的前提下，多模型/多卡吞吐随并行度线性增长；杜绝热卸载崩溃与锁竞争。

*本次实例：全局锁使双模型并发退化为串行；改为按模型分锁后双模型恢复 ~2x。*

## 3. 组批：按资源预算，不按个数

**前因**：变长输入下，"16 个 batch"可能是 16 秒也可能是 480 秒。前者让加速器空转（kernel launch 开销占比过高），后者直接 OOM。重试逻辑若只是"整批失败→逐个重试"，P99 会被长尾拖垮。

**写法**：

- MUST 定义**资源预算**（音频总秒数 / 图像总像素 / token 上限三者取其紧），按预算累积切分 batch；个数上限只作第二道护栏。
- MUST 实现**收敛式降级**：整批失败 → 预算减半重试（≤3 次，减半后仍装得下时强制对半切以保证收敛）→ 退化为单片。重试判据区分 OOM/算子错误与业务错误，只有前者触发减半。
- SHOULD 为解码类模型设**输出上限**：上限决定 KV-cache 的最坏显存（线性关系）与最坏解码步数。取"业务 P99 输出 × 2~3"即可，超长用截断+标记而非无界生成。

**目的**：显存峰值可预测（≈ 预算值），OOM 从"整单失败"变为"多一两次小 batch 调用"；长短输入的吞吐方差收敛。

*本次实例：16×30s=480s 一次 encode 是 OOM 主因；180s 预算将其拆 ~3 批，峰值降至约 1/3；输出上限 1024→512 使 KV 上限减半。*

## 4. 稀疏跳过：不算即最快

**前因**：真实输入高度稀疏——会议录音 20~40% 是静音，扫描件里有大量空白页。任何加速手段（量化、编译、更好的 batch）都比不上"直接不算"。

**写法**：

- SHOULD 在预处理后加一道**廉价分类器**（能量阈值、空白页检测、置信度门），低于阈值的分片直接产出空结果，不进加速器。全空输入 MUST 零推理返回。
- 分类器 MUST 比模型前向便宜 ≥2 个数量级，且默认开启、可用开关关闭；阈值保守（宁可多算，不可漏算），漏算率单独做回归测试。

**目的**：与模型无关的线性收益，输入越稀疏赚得越多，且零显存代价。

*本次实例：rms<-40dB 静音跳过，会议类音频省 20~40% 前向。*

## 5. 预处理：快径、流式、不落盘

**前因**：预处理是 CPU  bound 且常被低估。典型浪费有三类：对已标准输入重复转码、整文件常驻内存、变长 batch 下反复 autotune。它们不消耗显存，却通过"喂不饱加速器"间接拉低吞吐。

**写法**：

- SHOULD 设**快径**：仅校验真正的数学前提（如采样率、声道数、色彩模式），满足则零拷贝直入；格式白名单之类的非数学条件一律不作快径判据。
- MUST 流式：禁止为中间产物落临时文件；大输入分块编解码，内存峰值与文件大小解耦。
- 性能敏感的全局开关（如 cudnn benchmark、torch.compile、量化）MUST 默认关闭、显式开启，且开启项必须有回落路径（编译失败→eager，量化缺依赖→fp16/bf16）。变长输入下默认开 autotune 类优化是负收益。

**目的**：预处理延迟从 O(文件大小) 降为 O(分块)，加速器饥饿消除；风险优化项不影响默认路径稳定性。

*本次实例：快径去 format 白名单后 FLAC/OGG/M4A 省一次子进程；benchmark 默认关消除变长抖动。*

## 6. 多设备：调度是独立抽象

**前因**：单卡写死的代码在多卡机器上必然闲置一半算力。而把"选卡"逻辑散落在每个引擎里，会导致策略不可测试、不可替换（least-loaded、轮询、亲和调度迟早要换）。

**写法**：

- MUST 将设备选择收敛为一个**调度器抽象**：输入各设备利用率/空闲显存（含 `VISIBLE_DEVICES` 类环境过滤与显式指定优先），输出目标设备；无卡回落 CPU。引擎代码禁止直写设备索引。
- 模型注册表 MUST 以 **(模型, 设备)** 为键保存副本；对外兼容层（如心跳的已加载模型列表）保持旧语义，明细另设通道。
- 监控 MUST 同时给**明细**（每卡利用率/显存）与**聚合**（峰值利用率、显存求和），前者给调度器用，后者给人看。

**目的**：加卡即加吞吐（推理是纯并行负载，双卡实得 ~1.8x）；调度策略可独立演进而不碰引擎。

*本次实例：least-loaded 调度使双卡从"一卡 100%+一卡 0%"变为双卡各 ~80%，P99 -40~45%。*

## 7. 关键路径卫生：side-channel 移出临界区

**前因**：上报、打点、扫盘天生想"顺手"放在主流程里。它们平时无害、抖动时致命：一次磁盘卡顿或对端超时会直接计入推理延迟。

**写法**：

- 推理临界区 MUST 只做计算：进度上报节流（时间间隔或增量水位，终态必报），磁盘扫描结果缓存（数十秒 TTL），文件写盘分块+移出事件循环。
- 对外契约的旧字段 MUST 保持兼容，新增信息走新增字段/明细通道，禁止为新功能改旧字段语义。

**目的**：P99 由计算决定，不由最慢的 side-channel 决定；控制器升级不依赖 Agent 同步发布。

## 8. 配置、测试与演进

- **配置**：每个调参 MUST 有收敛的默认值 + 显式覆盖（环境变量优先），风险项默认关；新增参数 MUST 登记到示例配置与 README 配置表。目的：行为可复现、可回滚。
- **测试**：TDD。契约测试（输出 schema）、故障注入（OOM、缺二进制、畸形输入、卸载并发）、性能回归（budget 切分、跳过率）三类缺一不可。并行分工时测试按文件拆分，禁止多 Agent 同写一文件（本次的实测教训）。
- **演进顺序**：先零风险项（输出上限、上报节流）→ 再结构项（细粒度锁、预算 batch）→ 最后重型项（新后端、量化、编译）。每步独立可验证、可回滚。

## 9. 迁移示例：新的 OCR 处理工作流

把上面规则逐条翻译为 OCR 语言，检验可迁移性：

| 规则 | OCR 实例化 |
|------|-----------|
| 五段管线 | 拉取图片 → 预处理（定向/去噪/切分 tile）→ 按像素预算组批 → 检测+识别 → 组装版式 JSON 并结算；识别函数内禁网络/落盘 |
| 细粒度串行 | 按 (OCR模型, 卡) 串行，不同模型（检测 vs 识别）或不同卡并行；绝不设全局 OCR 锁 |
| 资源预算 batch | 按 `tile总像素 ≤ N` 组批，而非"16 张图一批"；大图 OOM 时 tile 减半重试 |
| 输出上限 | 单 tile 识别文本上限（如 512→256），KV/解码步数线性下降 |
| 稀疏跳过 | 空白页/低方差 tile 直接空结果，对应 ASR 的静音跳过 |
| 预处理快径 | 已是标准分辨率灰度图则直入，不按扩展名白名单；大图分块解码 |
| 多设备 | 复用同一调度器抽象，OCR 引擎只声明"我要一块卡"，不写死索引 |
| 关键路径 | 逐 tile 进度节流上报；模型目录扫描缓存 |

如果你在设计新引擎时，对上表任意一行答不出"预算是多少、降级几次、阈值多少"，说明设计还没收敛，先别写代码。
